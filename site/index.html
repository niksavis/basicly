basicly

Most agent harnesses ship instructions and skills. basicly also ships the workflow and the state — a deterministic development loop, the work graph it derives progress from, and git gates that hold whether or not the model read the guidance.

What it is

Four pillars, not a bundle of files

Guidance and gates are the classic harness bargain: prose a model may ignore, plus checks that do not care whether it did. The other two are the difference — basicly owns the process the work moves through and the state that process reads.

And they are not four separate things. The loop, and every headless agent it dispatches, reads the artifacts pillar 01 emits — so the config layer's output is the orchestrator's contract. That is why one track can start on Claude and finish on Codex, and it is what a projector alone or an orchestrator alone cannot offer.

01 Guidance

One versioned YAML catalog, projected into what each tool natively reads: CLAUDE.md, AGENTS.md, copilot-instructions.md, skills, subagents, permissions.

Edit one fragment and every target regenerates consistently. Your overrides live in an overlay that upgrades never touch.

02 Gates

Git hooks across pre-commit, commit-msg and pre-push, plus agent hooks for Claude Code and Copilot, and a verify pipeline with fast, full and staged modes.

The model choosing to run a formatter is a different thing from the formatter running automatically. Where a hook can enforce a rule, the rule is a hook.

03 The loop

A development process shipped as commands: intake, classify, decompose, build, verify, ship, teardown, retro — driven the same way under Claude, Codex or Copilot.

Work builds in an isolated worktree. Run one track at a time, or fan out parallel lanes behind a supervisor and a serial merge queue.

04 The work graph

Issues, dependencies, gate results, checkpoints and evidence live in a tracked graph. The loop keeps no side-state: the phase a track sits in is derived from that graph.

So a session can crash, compact, or hand over to a different agent family mid-track, and the next command picks it up by re-reading the graph.

What makes it different

The process is code, and so is the enforcement

Plenty of projects ship an agent workflow. What is unusual here is that the workflow is deterministic engine code rather than prose an agent is asked to follow, and that the gates it runs are the same ones your commits already pass.

Concern A guidance-only harness basicly
The workflow Markdown describing the steps an agent should take Engine code with one command per phase boundary; anything fully deterministic is a command, never a procedure to remember
Enforcement Asks the model nicely; compliance depends on the prompt Git hooks and a verify runner. A required gate is never passed by a model, at any autonomy level
Progress state Plan files and conversation memory, which compaction loses A dependency graph the phase is derived from, so resume is a read rather than a replay
Authority An orchestrator agent decides what happens next Agents propose, the engine disposes. Every agent runs as a pure function of state and returns a proposal the engine validates
Autonomy Usually all-or-nothing Opt-in, four levels, granted only from a real terminal and recorded with a spend ceiling. Human checkpoints hold by default

Install

One command, into any git repo

With uv on the machine: 

$ uvx --from git+https://github.com/niksavis/basicly@v0.8.0 basicly install

No uv or Python yet? The bootstrap shim installs uv first, then runs the same command: 

$ curl -fsSL https://raw.githubusercontent.com/niksavis/basicly/main/.scripts/bootstrap.sh | sh

Windows (PowerShell):

> powershell -ExecutionPolicy Bypass -Command "irm https://raw.githubusercontent.com/niksavis/basicly/main/.scripts/bootstrap.ps1 | iex"
  • Upgrading is the same command with a newer pin — install is an idempotent converge, not a separate migration path.
  • Scoped to your stack. --technologies python,zsh ships only the catalog content that matches.
  • Reversible. basicly uninstall removes everything managed; your overlay survives.

How it works

Two planes that meet at the gates

The distribution plane turns authored sources into the files your agents read. The execution plane drives a unit of work through the loop. They meet in exactly two places: a dispatched agent's context is the projected guidance, and the loop's verify step runs the same checks the hooks run.

Orange nodes are human checkpoints. Scale out with basicly loop supervise: one worktree per work package, landed serially through a merge queue in dependency order, with conflicts bounced back to the lane that owns them rather than resolved at merge time.

  • Yours stays yours. Overrides and additions live in .basicly-local/; installs and upgrades never touch them.
  • Deterministic first. Plain git-tracked files — no daemon, no hidden state, no network calls at build time.
  • Blocked beats guessing. An agent that cannot resolve a required fact stops and surfaces the missing fact instead of inventing an answer.

Status

What has shipped

Running code only, along the same four pillars: every line below is in the tree today and exercised on this project's own development. What is not built is listed separately further down and never mixed in here, so a check mark on this page always means working code. There are no dates anywhere — this is a status map, not a schedule. Both lists move as features land.

01 Guidance

  • ✓ One catalog projected to Claude, Codex and Copilot
  • ✓ Drift gate run by CI
  • ✓ Path-scoped rules, so conditional guidance loads on a matching file instead of always
  • ✓ An invocation axis per entry: only model-invoked entries pay context load
  • ✓ A subagent's capability level is a portable tier — low, medium, high, maximum — never a provider model id. Pinning an id is refused at lint, because the same model is spelled differently on every surface that serves it
  • ✓ A committed model map that basicly install ships into your repo resolves that tier: 32 cells — four tiers across four vendors, each on the two surfaces that serve it, the vendor's own API and GitHub Copilot — every cell carrying that surface's own published cost and token limits. Five record a tier a surface does not serve and carry no model at all, so a lookup fails loudly instead of quietly running a different tier

02 Gates

  • ✓ Git hook floor across pre-commit, commit-msg and pre-push
  • ✓ Agent hooks for Claude Code and Copilot
  • ✓ Verify pipeline with fast, full and staged modes
  • ✓ A check may declare a repair, so a mechanically fixable failure is fixed rather than reported

03 The loop

  • ✓ Single-track loop, intake to retro, any agent
  • ✓ Worktree isolation per unit of work
  • ✓ Parallel lanes behind a supervisor and a serial merge queue
  • ✓ Autonomy grants with a spend ceiling, a decision queue and a confined decider
  • ✓ A checkpoint a grant declined says why it declined, so "no grant covers this" reads differently from "a covering grant refused over a wrinkle elsewhere in the session"
  • ✓ Token telemetry read from each adapter's own usage report — including Copilot's AI-credit spend, and a cached-versus-reasoning split for Codex, so a cached token is not priced as a fresh one
  • ✓ Release automation up to the annotated tag
  • ✓ Work is sized by the material a lane actually reads, not by the size of the files it names — measured over 185 (lane, file) pairs, a file under ~4,000 tokens is read whole and above that a lane takes out roughly 1,500 however large it is. A three-line fix in a 90,000-token module is dispatchable instead of refused
  • ✓ Every dispatch records the context it actually consumed beside the forecast that predicted it, so the estimator is checked against a measurement rather than against its own output

04 The work graph

  • ✓ Issues, dependencies, gate results, checkpoints and evidence in a tracked graph
  • ✓ Phase derived from that state, so resume is a read rather than a replay
  • ✓ Why a lane went when it did, recorded on its run marker: the dispatch rank always, plus the scheduler's score and rank whenever the scheduler ranked that lane
  • ✓ The shared tracker export is published atomically, so concurrent lanes cannot read it half-written, and a storage error is charged to the store rather than to the lane's rework budget

What is coming

Sequenced, not promised, and deliberately without dates. These are not built — nothing below is running code, and a settled design is not evidence that anything enforces it. The order lives in the implementation plan; the evidence each status requires is in the architecture reference.

Building now

  • ▶ A supervised multi-lane run with zero human interventions caused by a harness defect
  • ▶ A spend and wall-clock forecast per model, enforced when a pass is admitted. Today's forecast models the working set, and measurement says that is the weaker predictor: declared scope explains 9.5% of a lane's real context use, turn count 86.3%
  • ▶ Deterministic routing evals with a rank-1 rate in CI, and an eval case for every catalog entry
  • ▶ Every gate classified by type, severity required on judged output, and rework convergence detected from the open-finding set rather than the count
  • ▶ A tutorial and how-to layer, so a new consumer has a path from install to first shipped unit, and basicly install reports the capability tier it actually delivered

Designed, nothing built

  • ◇ A named role per judgment step, each with its own instructions, tool policy, tier and output contract
  • ◇ An owned in-process append-only event log, removing the external tracker binary from the critical path — with provenance on every edge and an fsck that makes "the log is the truth" checkable

Being measured — the result may cancel the work

  • ? Whether an individual guidance entry changes behaviour. Recall is measured; adherence is not, and recall is an upper bound on it
  • ? Cost per landed package
  • ? Whether deterministic AST localisation cuts what an implementer spends before its first edit
  • Some things are not planned, so absence above is not an oversight: an LLM orchestrator in control of the tracker, an agent-writable catalog, a maintained TUI, an external database or daemon, and agent-to-agent messaging. Each refusal has a recorded reason.
  • The evidence behind each line — what the capability is and where it lives in the code — is in the architecture reference, and every release is itemized in the changelog.
